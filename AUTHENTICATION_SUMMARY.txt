QUICK ANSWER TO YOUR QUESTIONS:

1. FRONTEND LOGIN LOGIC (app.js, utils/api.js)
   ────────────────────────────────────────
   ✓ How frontend calls /api/mp/auth/login:
     - app.login() calls wx.login() to get a WeChat code
     - Sends code to backend: POST /api/mp/auth/login { code }
     - Backend exchanges code for openid via WeChat API
   
   ✓ What frontend does with response:
     - Response: { token, userId, nickname, avatarUrl }
     - Stores token in BOTH:
       * app.globalData.token (memory - fast access)
       * wx.setStorageSync('token') (persistent storage)
     - Stores full userInfo in BOTH locations too
     - Token lasts 7 days

2. BACKEND LOGIN ENDPOINT (/api/mp/auth/login)
   ────────────────────────────────────────────
   ✓ Location: service/routes/mp/auth.js (lines 52-96)
   
   ✓ What it does:
     1. Receives { code } from frontend
     2. Exchanges code for openid via WeChat API (or mocks if MOCK_WX_LOGIN=true)
     3. Checks if user exists in users table by openid
     4. If NEW user:
        - INSERTs into users table
        - INSERTs into members table (loyalty program, level=1)
     5. If EXISTING user:
        - UPDATEs last_login timestamp
     6. Generates JWT token: { userId, openid } valid for 7 days
     7. Returns: { token, userId, nickname, avatarUrl }
   
   ✓ Returns to frontend:
     YES - returns avatar_url and nickname from users table

3. USERIINFO/AVATAR/NICKNAME STORAGE & USAGE
   ──────────────────────────────────────────
   ✓ Stored in THREE places:
     
     A. In-Memory (app.globalData):
        - app.globalData.token = JWT token string
        - app.globalData.userInfo = { token, userId, nickname, avatarUrl }
        - Used for quick access within app session
     
     B. LocalStorage (persistent):
        - wx.getStorageSync('token') = JWT token
        - wx.getStorageSync('userInfo') = Full userInfo object
        - Restored on app restart
     
     C. Database (users & members tables):
        - users table: openid, unionid, nickname, avatar_url, phone, real_name, etc.
        - members table: member_no, level, points, total_nights, etc.
   
   ✓ Used across app:
     - pages/profile/profile.js: Displays from globalData
     - pages/profile_edit/profile_edit.js: Fetches full profile via GET /api/mp/auth/profile
     - Any page that needs user data calls api.getProfile()
     - Member info (level, points) fetched via GET /api/mp/member/info

4. GETUSERPROFILE / GETUSERINFO / WX.GETUSERPROFILE CALLS
   ────────────────────────────────────────────────────────
   ✓ SEARCHED: No wx.getUserProfile() or wx.getUserInfo() calls found
   
   ✓ Why NOT used:
     - App doesn't request WeChat user permission dialogs
     - All user data comes from backend database (users table)
     - Only uses wx.login() to get authorization code
     - Backend handles user info retrieval and storage

5. SEPARATE USER PROFILE ENDPOINTS
   ────────────────────────────────
   ✓ YES - Three separate endpoints:
     
     a) POST /api/mp/auth/login [NO AUTH]
        Returns: { token, userId, nickname, avatarUrl }
        Purpose: Initial login, minimal user info
     
     b) GET /api/mp/auth/profile [REQUIRES AUTH]
        Returns: Full profile with member info
        Includes: nickname, avatar_url, phone, real_name, member_no, level, points, etc.
        Purpose: Fetch complete profile when needed
     
     c) GET /api/mp/member/info [REQUIRES AUTH]
        Returns: Member-specific info
        Includes: level_name, points, discount, icon, next_level_name, etc.
        Purpose: Display member level and loyalty info

6. MIDDLEWARE EXTRACTING USER INFO FROM TOKEN
   ───────────────────────────────────────────
   ✓ YES - mpAuth middleware (service/middleware/auth.js)
   
   ✓ How it works:
     1. All authenticated routes use @mpAuth decorator
     2. mpAuth extracts token from Authorization header: "Bearer <token>"
     3. jwt.verify() checks token signature and expiration
     4. Sets req.userId = payload.userId (from token payload)
     5. Sets req.openid = payload.openid (from token payload)
     6. Passes control to route handler
     7. Route handler uses req.userId to query database
     
   ✓ Applied to endpoints:
     - GET /api/mp/auth/profile
     - PUT /api/mp/auth/profile
     - GET /api/mp/member/info
     - GET /api/mp/orders
     - And all other protected endpoints

THE FLOW IN ONE PICTURE:

User Opens App
    ↓
app.onLaunch() checks storage for token
    ├─ Token found? → Load to globalData, ready to use
    └─ No token? → Silent login:
        ↓
        wx.login() → code
        ↓
        POST /api/mp/auth/login { code }
        ↓
        Backend: code → openid → check users table
        ├─ New user? → INSERT into users & members
        └─ Existing? → UPDATE last_login
        ↓
        Backend: jwt.sign({ userId, openid })
        ↓
        Return: { token, userId, nickname, avatarUrl }
        ↓
        Frontend: Store in globalData + localStorage
        ↓
        User can now make API calls

Later: User Makes API Call
    ↓
api.getProfile() in any page
    ↓
request() function:
  1. Get token from globalData or storage
  2. Add Authorization header: Bearer <token>
  3. Send GET /api/mp/auth/profile
    ↓
Backend: mpAuth middleware
  1. Extract token from header
  2. jwt.verify(token)
  3. Set req.userId = 123
  4. next()
    ↓
Route handler:
  SELECT * FROM users WHERE id = 123
  JOIN members, member_levels
  Return full user profile
    ↓
Frontend: Page receives data, displays it

IMPORTANT DESIGN DECISIONS:

1. NO WeChat Permission Dialogs
   - App never calls wx.getUserProfile() or wx.getUserInfo()
   - No permissions requested from user
   - All user data stored server-side in database

2. JWT-Based Authentication
   - Token contains: { userId, openid }
   - Signed with MP_JWT_SECRET environment variable
   - Expires in 7 days (configurable)
   - Sent via Authorization header

3. Dual Storage
   - Memory (globalData) for fast access
   - LocalStorage for persistence across sessions
   - Both updated on every login

4. Silent Login on Startup
   - If no token found, automatically logs in
   - Errors caught silently, won't block app startup
   - User won't see login failures initially

5. Lazy Loading
   - Login returns minimal info: token, userId, nickname, avatarUrl
   - Full profile fetched separately when needed
   - Member info fetched separately from /member/info

6. First-Time User Handling
   - Automatically creates users table row
   - Automatically creates members table row (level=1)
   - Generates member number: M202504000001 format
   - No manual user creation needed
